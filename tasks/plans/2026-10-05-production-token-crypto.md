# SA-004 生产 Git Token 加密配置与恢复验证

## 目标与授权

用户要求继续当前 HEAD。修复已有 AES-GCM 能力没有接入生产部署配置的问题，并补齐错误密钥、损坏密文和恢复后的验证行为。继续保留上一项 SA-017 的未提交改动，不覆盖已有工作。

最终行为：`prd,real` 默认加密，部署者提供独立 Base64 32 字节密钥；仓库及 Settings Token 写入带 `enc:v1:` 标识的密文。缺失或格式错误的密钥不能启动；有标识密文不能解密时拒绝启动或读取，不能将密文冒充 Token 继续调用 GitLab。相同密钥下重启、数据库备份恢复后，凭据仍可正确用于连接。

## 完整范围与模块边界

- Domain / Application / API / Frontend：复用现有 Token、Settings、仓库、连接测试及脱敏接口，不增加密钥管理或公开解密 API。
- Infrastructure：生产密钥供给、加解密错误边界、只读启动校验；不输出密钥、Token 或密文。
- 配置与部署：生产开启加密和存量校验，Compose 和示例环境文件要求显式提供独立密钥。
- 数据：不新增迁移，不访问或重写用户现有数据库，不轮换真实密钥。
- 兼容：无标识明文/旧密文保持既有兼容读取；其格式无法可靠区分，不能宣称已经迁移或能检测所有旧密文错钥。
- 运维：数据库备份不包含密钥；恢复必须独立保管并提供原密钥，先在隔离库演练。
- 测试：转换器错误边界单测；真实 PostgreSQL 生产配置的双字段加密、重启、pg_dump/psql、错误密钥和损坏密文；GitLab HTTP fixture 只验证凭据使用，不宣称真实 GitLab 发布验收。

## 风险与回滚

- 新部署必须保存密钥；丢失密钥无法从数据库备份恢复 Token，需从可信来源重新录入。
- 既有加密实例必须沿用原密钥，不得生成新密钥覆盖；旧明文数据先备份、复核，再单独安排迁移。
- 不支持用关闭加密绕过已加密数据错误，也不把恢复备份当作密钥轮换。
- 仅回退应用不应丢弃密钥；恢复时同时匹配数据格式、应用版本和原密钥。
- 本轮仍不覆盖真实 GitLab 发布、浏览器用户旅程和完整镜像构建；测试 fixture 和真实业务验收明确区分。
